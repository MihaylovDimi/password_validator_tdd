# Reflection: TDD and the Password Validator

Having a full suite of tests helps me keep a sustainable pace, because I can check that each change works without breaking rules that are already in place. With TDD, I first write a test for one specific requirement and then add the simplest code that makes it pass. When we added the digit rule, the tests for the empty password and the minimum length kept checking the old behaviour, and the same happened when the special character rule was added. This way I find mistakes early and can change the code step by step, instead of writing everything at once. Writing the test first also shaped the design: each rule became its own small function, which made the next rule easy to add. This reflects the Agile principles of sustainable development and continuous attention to technical excellence.

If the minimum length changed to 10 tomorrow, I would be fairly confident that the other rules would still work. I would only need to change the `MINIMUM_LENGTH` constant from 8 to 10, which is a single line, while the digit and special character checks stay untouched. I would then run the whole test suite. The boundary tests would also need updating, because an 8-character password would no longer be valid. The tests give me confidence that the change is controlled and that the rest of the logic still works.
